Idle Elite Agent Readability Goal Checklist

Use this checklist as one continuous agent goal: make the codebase easier for future agents to understand, navigate, validate, and safely refactor. Do not create a separate goal for each checklist item. Treat the items below as phases inside one run, with small commits at the end of each coherent work package.

Start One Master Goal

Paste this into a fresh agent thread from the Idle Elite worktree:

/goal Execute docs/agent-readability-goal-checklist.html as one agent-readability improvement run. Work through every phase in order, but do not stop after one checklist item unless blocked. For each work package: inspect the current codebase before changing it, preserve gameplay and visuals unless the checklist explicitly requires a behavior-preserving move or rename, inspect references before renaming or moving files, update code/assets/import metadata/docs/tests together, run focused validation plus .\scripts\check-project.ps1 when practical, verify no headless Godot process was left behind, record progress in the checklist or a linked status note, commit, push to the current branch, then continue with the next work package until all acceptance criteria are met or user input is required.

Execution Model

  • Run this as one master goal, not as many separate goals. The agent should keep momentum across phases.
  • Use phases to organize thinking, commits, and validation. A phase may contain several commits when the changes touch unrelated files or risks.
  • Break a phase into smaller work packages only when a change crosses ownership boundaries, touches generated files, moves assets, or needs separate validation.
  • Commit after each coherent package, not after every tiny bullet and not after an oversized mixed refactor.
  • Pause for user input only when compatibility, visual changes, save migration, deletion of uncertain assets, or external credentials are required.
  • Prefer documentation and ownership maps before broad refactors. Later code moves should rely on those maps.

Phased Work Plan

Phase 1. Build The Orientation Layer

Start by documenting the map future agents need before they touch risky code or assets. This phase should usually be one or two docs-only commits.

1.1 Create the agent-facing codebase map

docsorientation Highest value first because it helps every later phase move safely.
  • Create or update a concise codebase map for future agents.
  • Explain runtime asset structure, source archives, generated files, activity database ownership, Godot validation rules, and risky paths.
  • Include where major systems live in scripts/main.gd and which areas are safe or risky to refactor.

Done: added docs/agent-codebase-map.md, linked it from README.md and docs/README.md, and covered runtime/source asset ownership, generated files, activity database sync/audit rules, validation commands, and risky paths.

1.2 Document scripts/main.gd ownership regions

code mapmain.gd Main readability blocker for agents.
  • Map ownership regions for UI, activity, save/load, ads, leaderboard, chat, shop, hub, profile, and asset paths.
  • Identify safe extraction targets without performing broad refactors yet.
  • Note existing tests that protect each area.

Done: added docs/main-gd-ownership-map.md with approximate line regions, subsystem ownership, safe extraction targets, rename boundaries, and focused validation commands for UI, activity, save/load, ads, leaderboard, chat, shop, hub, profile, fishing, audio, and asset paths.

Phase complete when a new agent can find major systems, known risky areas, validation commands, source/generated ownership, and the current validation baseline without reading commit history.

Phase 2. Audit And Classify Asset Ownership

Inventory before moving anything. This phase answers what is runtime-critical, generated, source/provenance, stale, or unsafe to touch.

2.1 Audit remaining source and archive asset folders

assetsaudit Clarifies what should be preserved before deleting or moving anything.
  • Focus on docs/art-source, assets/loading, assets/android, export presets, and import metadata.
  • Document folders to preserve, rename, clean, or skip.
  • Separate runtime assets from source/generation/provenance assets.

2.2 Clean docs art-source archives

docs/art-sourcecleanup Source history should be useful, not a pile of mystery generations.
  • Make source/archive folders and filenames describe domain, status, and relationship to runtime assets.
  • Remove only proven-unused bad generations after reference and hash checks.
  • Preserve useful provenance and final-selection notes.

Phase complete when asset/source folders have explicit ownership notes and any cleanup has evidence from reference searches, hashes, or import metadata. Uncertain assets should be documented, not deleted.

Phase 3. Align Critical Runtime Assets

Handle boot and platform assets separately because they are externally referenced and easier to break than ordinary UI art.

3.1 Align loading and boot-screen assets

loadingGodot High impact, but risky because boot paths are project-level.
  • Audit assets/loading, project.godot, boot loading scripts, tests, and import metadata.
  • Rename only clear active assets and remove only proven stale variants.
  • Do not change loading visuals or behavior unless required to preserve references.

3.2 Align Android launcher and export assets

androidexport Keep launcher/export references exact.
  • Audit assets/android, export_presets.cfg, source files, and docs.
  • Make launcher icons, adaptive foreground/backgrounds, preview icons, and source files understandable at a glance.
  • Validate export preset references after every move.

Phase complete when boot/loading and Android/export references are readable, exact, and validated. Commit loading and Android work separately.

Phase 4. Make Runtime Ownership Durable

Turn the maps into code organization improvements, keeping behavior and visuals unchanged.

4.1 Extract asset path ownership

constantstests Make file/code alignment durable.
  • Move or organize asset path constants into clearer sections or modules following existing project style.
  • Update tests so important resource paths remain protected.
  • Do not change image content, import settings, gameplay, or visuals.

4.2 Refactor navigation, home, shop, chat, leaderboard, and profile UI boundaries

UIrefactor Split by user-facing ownership, not arbitrary helper buckets.
  • Extract or reorganize code in small commits with no behavior or visual changes.
  • Keep names domain-accurate: navigation, hero/home, shop, chat, leaderboard, profile/avatar.
  • Update focused regression assertions after each extraction.

4.3 Refactor activity detail, cards, mastery, unlocks, and offline summary boundaries

activity UImastery High-impact reviewer surface.
  • Clarify modules and naming for activity detail, cards, mastery medals, lockpads, and offline summary.
  • Keep asset paths and constants aligned with any extracted code.
  • Run focused UI/resource regression checks after each commit.

Phase complete when high-traffic UI and asset ownership are easier to locate, protected by focused checks, and behavior-neutral. Split commits by subsystem so failures can be bisected.

Phase 5. Clarify Data, Naming, And Generated Rules

Clean the contracts that future agents are most likely to misunderstand: generated data, generic names, and file hygiene.

5.1 Clarify activity database contracts

activity databasegenerated data Make source/generated ownership unambiguous.
  • Document how docs/activity-database.json, generated JS, runtime loading, docs, and validation scripts relate.
  • Make helper names and checks clear where data contracts are opaque.
  • Always sync and audit after source JSON edits.

5.2 Rename generic internal variables and functions in high-traffic paths

namingbehavior-neutral Treat naming as architecture, not churn.
  • Look for generic names like data, item, info, tmp, value, and obj only in high-value areas.
  • Rename only internal identifiers where the role is clear and behavior-neutral.
  • Do not rename serialized keys, data IDs, node names, signals, input names, or user-facing strings without compatibility handling.

5.3 Clean generated, cache, output, and import metadata rules

generated filesgit hygiene Prevent future agents from committing noise.
  • Document which files are tracked, ignored, regenerated, deleted, or never touched manually.
  • Normalize rules for .import, .uid, output folders, build folders, and local config.
  • Fix stale docs if ignore/build behavior has changed.

Phase complete when data source/generated relationships, naming boundaries, and generated-file rules are explicit enough that an agent can make a small change without guessing which files are authoritative.

Phase 6. Reconcile And Close The Loop

Finish by making sure the docs, tests, and new-agent instructions describe the architecture that actually exists after the work.

6.1 Update docs and tests to match current architecture

docstests Documentation should not describe old paths.
  • Search docs/tests for stale paths, old folder descriptions, old architecture language, and obsolete validation notes.
  • Update or remove stale references in small commits.
  • Keep generated docs/data in sync with their sources.

6.2 Final agent readability audit

final auditonboarding Close the loop with a fresh-agent checklist.
  • Review whether a new agent can identify important folders, generated files, validation commands, and risky areas quickly.
  • Produce a concise new-agent onboarding checklist.
  • List remaining risky areas that should not be renamed without deeper compatibility work.

Phase complete when the final docs match the post-refactor tree, validation status is recorded with exact known blockers, and the checklist itself no longer contains stale instructions.

Per-Item Completion Rule

Do not mark an item complete just because a broad scan was run. An item is complete only when the intended docs/code/assets/tests are updated together, focused validation passes, the known full-suite blocker is recorded if present, no headless Godot process is left behind, and the work is committed and pushed.
