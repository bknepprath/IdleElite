Fishing Scroll Lag Investigation

Purpose: keep the investigation from looping. Each suspect has one or more concrete methods. When a method has been attempted, it is checked off. Do not repeat a checked method unless a new, different method is added under the same suspect.

Current confirmed symptom: manual click/touch drag has a large freeze before scroll starts, then scroll motion is mostly smooth. The cold drag probe captured press-frame spikes up to roughly 813ms, while motion frames were usually around 8-9ms.

Checked Methods

Suspect: fishing gear wallet taps are being swallowed by the scroll fast path

checked
Method: route fishing wallet press input before scroll-mode cleanup, deferred swipe startup, and fishing scroll bypass checks.
  • Evidence: _route_fishing_wallet_unhandled_input() was late in _input(), after fishing deferred-scroll and detail-routing returns.
  • Failure mode: tapping the fish/gear circle could start scroll cleanup or deferred-swipe handling first, making the wallet appear dead while still doing laggy work.
  • Fix attempted: moved the wallet route immediately after _note_player_input() so wallet taps win before fishing scroll logic can claim the press.

Suspect: all fishing area modules being mounted at once is the core cause

checked
Method: run an all-mounted web stress path with every fishing module present.
  • Evidence: web no_lazy stress held 21/21 modules mounted.
  • Result: worst Godot frame about 17.56ms, worst browser RAF about 35.32ms, no frames over 50ms.
  • Conclusion: module count alone is not sufficient to explain the severe hitch.

Suspect: warmed scroll path is inherently slow

checked
Method: measure repeated production web touch and desktop mouse drags after setup.
  • Evidence: production web drag probe passed with worst Godot frame about 32.89ms and worst RAF about 35.32ms.
  • Result: no visible placeholders, no culled modules overlapping the viewport, no frames over 50ms.
  • Conclusion: warmed scroll motion can be smooth in the harness; the player-facing problem is likely before or during the first drag start.

Suspect: first drag motion frames are the expensive part

checked
Method: add cold drag probes that record press and motion samples separately.
  • Evidence: worst samples were consistently phase=press, not phase=motion.
  • Result: press samples reached about 813ms; motion samples stayed roughly 8-9ms.
  • Conclusion: the freeze happens before useful drag scrolling starts.

Suspect: queued fishing settle warm mount is allowed to run during manual interaction

checked
Method: count primary pointer down as active fishing scroll interaction and add a hard warm-mount pause while interaction is active.
  • Files touched: scripts/main.gd.
  • Evidence: after patch, cold drag test still showed press-frame spikes around 813ms.
  • Conclusion: this exact method did not fix the freeze. Do not repeat it as-is.

Suspect: new fishing art size/background replacement is the only cause

checked
Method: switch fishing area/background rendering to flatter art path and compare scroll probes.
  • Evidence: art quality changed, but user still reported lag; harness still reproduced cold press spikes.
  • Conclusion: art may contribute to mount cost, but flat art alone did not remove the freeze.

Open Suspects

Suspect: process-frame measurement is incorrectly charging idle warm work to the press sample

checked
Method: split the cold drag probe timing into direct input dispatch time and following frame process time.
  • Evidence: worst sample was mouse-up press with frame_ms=860.082, main_input_ms=859.73, scroll_input_ms=0.025, and process_frame_ms=0.293.
  • Result: the bad time is inside main._input(event), not the next frame and not the scroll container input handler.
  • Conclusion: pursue press-routing instrumentation next. Do not keep patching process-frame warm queues as the primary method.

Suspect: visible viewport fill is mounting too many modules synchronously during cold probe setup or first scroll settle

checked
Method: cap synchronous visible_viewport_fill callers to one module per frame during scroll settle and new press cleanup.
  • Evidence: _finish_fishing_scroll_perf_probe() and _set_fishing_scroll_mode_active(false) called _sync_fishing_detail_visible_viewport_cards(-1), which meant unbounded visible mounting.
  • Fix attempted: added FISHING_DETAIL_VISIBLE_SETTLE_FILL_BUDGET := 1 and used it for scroll-settle and new-press cleanup fills.
  • Result: cold drag probe passed with max_ms=17.782, p95_ms=8.378, over50=0.
  • User report: after this change, desktop Godot scrolling felt smooth.

Suspect: web probe was run against a stale exported build

open
Method to attempt: rebuild/export web after the visible-fill cap, then rerun production and all-mounted web probes.
  • Evidence to investigate: after the local fix, production web probe reported one 50.408ms Godot frame, but the web harness reads builds\web.
  • Risk: if builds\web was not re-exported after the final code change, the web result measured old code.
  • Success condition: fresh production web and all-mounted web probes both stay under 50ms.

Suspect: active render-culling sync causes one web drag-frame hitch after all modules are mounted

open
Method: throttle active fishing render-culling updates more aggressively during drag.
  • Evidence to investigate: fresh production web probe failed on first mobile drag with mounted=21/21, rendered=11, culled=10, maxFrameMsec=53.165, and rafMaxMsec=52.895.
  • Fix attempted: increased active culling step/minimum time to reduce culling frequency during drag.
  • Result: fresh production web still failed, worse, with maxFrameMsec=62.952 and rafMaxMsec=58.725.
  • Conclusion: throttling active culling is not the right method.
Method to attempt: restore/disable fishing render culling once all lazy modules are mounted.
  • Evidence to investigate: the web failure state already has mounted=21/21, while earlier all-mounted/no-culling ablation stayed under 50ms.
  • Success condition: fresh production web and all-mounted web probes stay under 50ms with no visible placeholders or visible culled modules.

Suspect: press input still routes through expensive hit scans for fishing area/method controls

open
Method: time high-level fishing press routing branches in main._input.
  • Evidence: branch trace showed input_defer_tap_check_false and input_defer_tap_check_true samples around 130-206ms.
  • Evidence: branch trace also showed fishing_detail_route samples around 125-208ms after the defer check returned false.
  • Conclusion: the hot path is inside fishing press routing, but this method is too coarse to name the exact inner scan.
Method: time inside _fishing_detail_primary_press_should_defer_tap_scan, _fishing_detail_primary_press_skips_global_button_scan, and _route_fishing_detail_input.
  • Evidence: fishing_skip_scan_page_switch_false took roughly 120-238ms before the fishing press could proceed.
  • Fix attempted: added a page-switch-only helper so fishing press routing does not call the expensive _action_card_at_position scan just to exclude page-switch buttons.
  • Result: worst cold drag press sample dropped from about 981ms to about 328ms.
  • Conclusion: page-switch hit testing was a real offender, but not the last one.

Suspect: repeated mount/unmount thrashing rebuilds the same fishing area modules over and over

open
Method to attempt: count per-track mount frequency during one drag test and fail if the same area is rebuilt repeatedly.
  • Evidence to investigate: traces repeatedly show entries like fishing:area-beach-0 being mounted in settle_warm_process.
  • Potential fix if proven: stop freeing fishing area nodes during the active page lifetime, or keep a lightweight root cache that does not re-run expensive construction.

Suspect: UI/style/theme synchronization after lazy mount is causing second-order frame spikes

open
Method to attempt: isolate lazy mount construction time from post-mount UI synchronization time.
  • Goal: separate _detail_lazy_mount_item construction cost from _update_ui, scroll-limit sync, render culling, and placeholder repair.
  • Potential fix if proven: batch or defer post-mount sync until after interaction settles.
