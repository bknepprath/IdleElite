UI Navigation Controls Plan

Planning notes for page switching, persistent bottom controls, favorites, sorting, pinning, and module collapse behavior.

Large UI update

Make every page easier to steer.

This update adds two kinds of navigation: local page-to-page movement at the bottom of each page, and a compact control dock above global chat for favorites, sorting, skill navigation, and other high-use actions.

Goal

Reduce long-scroll friction, make favorite modules feel collectible, and give players a reliable place for page navigation without crowding the page header.

Design Tone

Buttons should feel chunky, readable, toy-like, and intentional: black strokes, clear silhouettes, strong page colors, and icons that are understandable even before reading the label.

Layout Rule

The bottom-most module on every scrollable page needs extra bottom spacing so the new dock never covers usable content when the player scrolls all the way down.

Accepted MVP

DecisionDirectionWhy
Dock size Use four equal slots above chat: Favorites, Sort, Skills, Active/Ready. Four is enough for thumb-friendly controls without shrinking labels into noise.
Skills location Move the current Skills/back-to-skills affordance into the dock on skill detail pages. This is navigation, so it belongs with persistent navigation. It also clears the page header for page identity and contextual tools.
Fourth button Make it adaptive: Active when an action is running, Ready when claimable/important modules exist, disabled otherwise. This gives the slot a reason to exist every session and avoids using a generic overflow button as a home for weak features.
Page switch wrapping Skill detail pages wrap in a ring: Fighting, Thieving, Building, Woodcutting, Fishing. The player never reaches a dead end, and the destination-colored buttons teach the skill map over time.
Favorites view Show compact favorite module rows first, with a tap opening or jumping to the full module. A full-module favorites wall can become huge. Compact rows make favorites a command center instead of a second long scroll.

Page Switch Module

  • Appears as the final content module in every page stack.
  • Contains exactly two buttons: previous neighbor and next neighbor.
  • Each button inherits the destination page's theme color and displays the destination name.
  • Use readable labels such as Building, Fishing, Fighting, not vague Previous or Next.
  • Skill detail pages wrap in the ring shown below. The skill hub can get its own rule in a later pass.

Module Dropdown

The dropdown should be a real menu state, not three always-visible buttons. The module itself keeps one consistent menu button so dense pages stay clean.

Module State Model

PinnedStored per page/module. Pinned modules render above normal modules, still inside their page, and keep their normal module behavior.
FavoriteStored globally by stable module key. Favorites appear in the Favorites view even if they are not pinned.
CollapsedStored per module. Collapsed modules render as compact headers with name, status, and menu button; never disappear entirely.
SortedView preference, not module identity. Sorting rearranges normal modules after pinned modules are placed.

Ordering Rules

  1. Pinned modules render first, in the order the player pinned them.
  2. Favorite status does not change ordering unless Favorites view is active.
  3. Sort mode applies after pinned modules and before the page switch module.
  4. Collapsed state affects height only; it must not remove the module from sort or favorite logic.
  5. The page switch module is always last and cannot be pinned, favorited, collapsed, or sorted.

Bottom Dock Buttons

ButtonIcon DirectionStateNotes
Favorites Big star, trophy-star, or heart-star. Avoid tiny detail. Toggle. Active while favorites list is open. Shows favorited modules from all pages. Empty state should say there are no favorites yet and point players toward module menus.
Sort Stacked bars, A/Z badge, or three module tiles rearranging. Opens a small mode menu. Options: level order, module type. Later: recently used, favorites first, available actions first.
Skills Left arrow into a five-dot skill cluster, or simple back arrow plus skill badge. Navigation action. Recommendation: move the current top-left Skills button here. It belongs near other persistent navigation.
Active/Ready Exclamation mark, lightning bolt, or running boot. The icon should look urgent but not like an error. Adaptive action. Priority: running action first, claimable passive/reward modules second, next newly unlocked module third.

Later Button Ideas

  • Collect Ready: keep as part of Active/Ready first; split only if it becomes important enough.
  • Active Task: keep as part of Active/Ready first; the label can change based on state.
  • Compact View: toggles collapsed summaries for players managing many modules.
  • Filters: show only unlocked, available, passive, active, or reward-ready modules.

Recommendation

Start with four dock buttons: Favorites, Sort, Skills, Active/Ready. This gives the player two organization tools, one navigation escape hatch, and one context-sensitive jump button.

Persistence

  • Pinned modules should persist per page.
  • Favorites should persist globally.
  • Collapsed modules should persist per module.
  • Sort mode can start session-only if persistence is risky.

Implementation Checklist

7 Implement sort modes. Level order and module type sorting work for the current page without displacing pinned modules.

Remaining Decisions

  1. Should the skill hub itself get a page switch module, or should this first pass limit the switch module to skill detail pages?
  2. Should Sort mode persist permanently per page, or reset each session until we see how players use it?
  3. Should Active/Ready prefer claimable passive rewards over the running action when both are available?
  4. What exact icon set should be drawn for Godot: text-glyph prototype first, or custom cartoony texture buttons immediately?
